# 项目军规：统一 AI 代码质量审查

> 本文是 `ai-code-review` 的产品目标与架构决策基线。任何新增分析器、工作流、配置项、输出协议或平台接入都必须满足以下军规；若与示例、历史设计或局部便利性冲突，以本文为准。

## 1. 根本目的

`ai-code-review` 的根本目的，是在 **人工 Code Review 之前和过程中**，对已提交代码改动提供统一的 AI 辅助质量审查。

它以基础语法、类型、SAST、密钥扫描和测试等确定性分析为证据基础，并由 AI 综合理解本次改动的业务与技术影响，识别潜在缺陷、边界遗漏、跨文件影响、设计风险和可维护性问题，最终为人工
reviewer 提供可追溯、可行动的审查参考。

它不承诺替代人工判断，也不把模型文本当作自动化事实。

## 2. 不可违反的产品军规

1. **一个产品入口。** 对调用方而言，`ai-code-review` 是唯一的评审能力和统一输出入口；默认工作流名称与 PR/MR 评论应表达“AI
   Code Review”，不能把 Java、CodeQL、PMD、SpotBugs 或某个模型包装成彼此独立的评审产品。
2. **分析器是阶段，不是产品分叉。** Java AST、CodeQL、PMD、SpotBugs、SARIF、TypeScript、密钥扫描、测试和 DeepSeek
   都是统一评审流水线中的分析或验证阶段，必须共享领域模型、证据规则、预算、结果协议和最终汇总。
3. **AI 是核心审查能力。** 确定性工具负责提供可验证事实与定位证据；AI
   负责结合改动上下文分析缺陷、影响范围、行为回归、边界条件、设计与可维护性风险。不得把项目退化为仅转发静态扫描结果的工具。
4. **人工审查优先。** AI 的语义结论默认是 `grounded` 人工审查建议；只有独立确定性证据验证的事实型发现才可成为 `verified`
   ，并按显式策略参与质量门禁。任何配置不得把单纯 AI 文本提升为阻断依据。
5. **一份统一结果。** 同一 PR/MR 的日志、摘要评论、通知和机器结果必须汇总确定性发现、AI 建议、抑制项与投递状态，而不是要求
   reviewer 在多个互不关联的工作流之间拼接结论。
6. **只审查已提交改动。** 所有结论必须锚定明确的提交范围与安全 `DiffChunk`；不读取未提交工作区作为评审输入，不把无法定位的外部工具或模型结论当作当前改动的问题。
7. **安全边界不能为统一体验让步。** 不执行不可信 PR 脚本来换取分析能力；密钥、私钥、Token、完整
   diff、敏感路径和敏感内容不得进入日志、评论或模型输入。工作流内部可以按权限与执行风险拆分步骤或任务，但对外仍属于一次统一评审。
8. **扩展依赖统一契约。** 新模型、新语言和新扫描器通过端口、分析器身份、统一候选发现项和 SARIF
   等适配层接入；领域层与评审用例不得依赖具体供应商、语言构建工具或 Git 平台。

## 3. 统一评审心智模型

```text
已提交 PR / MR / 手动范围
             |
             v
  基础确定性分析（语法、类型、SAST、测试、密钥）
             |
             +----> 可验证事实与安全定位证据
             |
             v
  AI 变更理解（行为、影响、缺陷、边界、设计、可维护性）
             |
             v
  统一证据校验、策略与汇总
             |
             v
人工 reviewer 的一份 AI Code Review 摘要
```

## 4. 对后续实现的约束

- Java 支持的下一步是将 CodeQL、PMD、SpotBugs 等作为 `ai-code-review.yml` 内的可选确定性阶段接入，并把其 SARIF 与 AI
  结论汇总；不是要求用户维护另一套 Java 评审产品。
- 若安全隔离需要分成无 Secret 扫描任务与有权限的评论/汇总任务，二者必须以同一 `runId`、提交范围和统一评论协议关联，并在文档中解释为同一次评审的内部阶段。
- 新规则与新模型必须提升“人工审查参考”的覆盖与可信度；若只增加配置复杂度、重复评论或孤立检查，则不应实现。
